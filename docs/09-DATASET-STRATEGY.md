# 09 — Dataset Strategy

Three datasets, kept **separate** (different schemas, contexts, label meanings; never merged or pooled for metrics). Datasets are not in the repo; `datasets/README.md` will document download steps (Kaggle account needed — user action). Raw files git-ignored.

| Dataset | Size | Role | Schema notes | Key cautions |
|---|---|---|---|---|
| **PaySim** (primary) | ~6.36M rows | Platform development; all modules (ML, behavioral, graph, duplicates-by-transaction, risk, alerts) | `step` (hour, 1–743), `type` (PAYMENT, TRANSFER, CASH_OUT, DEBIT, CASH_IN), `amount`, `nameOrig`, `oldbalanceOrg`, `newbalanceOrig`, `nameDest`, `oldbalanceDest`, `newbalanceDest`, `isFraud`, `isFlaggedFraud` | Synthetic. No real timestamp → map `step` to `epoch + step hours` (configurable, stored as `step` and derived `occurred_at`). Fraud only in TRANSFER/CASH_OUT. Merchant accounts (`M…`) have no balance info. Balance fields leakage-prone. Very few repeat sender accounts → behavioral/graph signal sparse; cold-start handling matters. |
| **ULB credit-card** | 284,807 rows, 492 frauds | Independent supervised/unsupervised benchmark (imbalance 0.172%) | `Time`, `V1–V28` (PCA), `Amount`, `Class` | No account IDs → **no behavioral/graph/duplicate modules**; ML benchmark only, not loaded into the account-based platform tables (kept in `ml_engine/experiments` loader, optionally importable as a dataset with `sender` absent). |
| **Elliptic Bitcoin** | 203,769 nodes, 234k edges | Graph-learning experiments (RQ2, GNN gate) | node features (166), time steps 1–49, labels licit/illicit/unknown (~77% unknown), edge list | Bitcoin transactions as nodes (not accounts); anonymised features. Separate experiment pipeline; not imported into the transaction tables. |

## Handling decisions
- **Loading PaySim:** pandas chunked reading → Postgres `COPY` into staging → upsert accounts → insert transactions; benchmark on 100k → 1M → 6.36M. The Phase 4 acceptance test uses a 100k sample first (dev), full file as a stress test (Phase 15).
- **Development subset:** deterministic stratified-by-time subset (e.g., first N steps, all fraud rows in those steps) so UI/tests run quickly. Documented so numbers are not mixed with full-dataset results.
- **Labels:** `ground_truth_label` stored on transactions *only* for evaluation/analytics ("detection performance", "false-positive analysis"); never displayed to analysts as if it were a model prediction, and hidden from non-research views by default.
- **Test fixtures:** tiny synthetic CSV/XLSX generated by script (clearly labelled mock) for unit tests; includes malformed rows, duplicate IDs, missing columns.
- **Demo data:** an additional seeded scenario script plants the "5 × ₹40,000 in 10 minutes" pattern and a chain/cycle in a *clearly labelled demo dataset* for live demonstration; never mixed into metrics.
- **Invoices (Module 5):** no public ground-truth set assumed; build a small synthetic invoice generator (PDFs/images with controlled duplicates/variations) and, if available, a public invoice sample (e.g., SROIE/RVL-CDIP subsets — licensing to be checked) for OCR quality checks. OCR accuracy will be reported on this set only.
- **Compliance:** only public/synthetic data; license/citation recorded per dataset in `datasets/README.md`.

## Import mapping for PaySim (Phase 4)
Preset `paysim` (auto-detected in the preview): `step→step`, `type→tx_type`, `amount`, `nameOrig→sender`, `nameDest→receiver`, balances→`sender/receiver_balance_before/after`, `isFraud→ground_truth_label`; `isFlaggedFraud` is left unmapped so it lands in `metadata` (excluded from ML features). Time: `occurred_at = 2026-01-01T00:00Z + step hours` (arbitrary epoch, configurable; PaySim has no real clock). Accounts with prefix `M` are typed merchant, `C` customer. No transaction-ID column exists in PaySim, so IDs are generated as `G<dataset>-<job>-<row>`. Download from Kaggle is still a manual step (needs your account); until then `python manage.py generate_mock_paysim_csv` produces a random PaySim-format file (labelled mock) for testing — never use it for research metrics.
