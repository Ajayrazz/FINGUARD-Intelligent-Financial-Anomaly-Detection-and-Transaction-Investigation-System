# 17 — Known Limitations (living document)

## Anticipated (from design; to be confirmed or retired by experiments)
- PaySim and Elliptic are synthetic/anonymised; results do not transfer to real banks. ULB features are PCA-anonymised (explanations limited to V-names).
- PaySim has no real timestamps, little repeat-sender history, and leakage-prone balance fields; behavioral and graph signals may be weak there.
- ULB has no account IDs, so behavioral/graph/duplicate modules cannot be evaluated on it.
- Unsupervised detectors produce false positives; LOF/OC-SVM scale poorly (subsampling required).
- SHAP/LIME are approximations, can be unstable, and are not causal proof.
- Graph algorithms (cycles, betweenness) are expensive on millions of edges; bounded search and subset projections are used.
- OCR accuracy depends on scan quality; evaluated only on a synthetic/public sample.
- Risk weights/thresholds are research proposals, not regulatory standards; calibrated only on the available labels.
- Email notifications use console/SMTP-test backend unless configured.
- Real-time event streaming (Kafka) is not implemented; API ingestion is micro-batch.
- Host Python/Node versions differ from the containerised runtime (D-002).

## Discovered during implementation
- Phase 2: the Users/Audit/Login pages were type-checked, built and unit-tested (auth guards, login form, API client) but **not driven in a real browser**; the API behind them was exercised end-to-end with real logins. Browser E2E (Playwright) is planned for Phase 13/15.
- Audit trigger can be removed by a database superuser; production DB roles should not be superuser (Phase 16).
- No password-change self-service or forced password rotation yet; only admin reset.
- Access tokens are not revocable before their 15-minute expiry (refresh tokens are). Role/permission changes apply on the next request because permissions load per request.
- `/ws/echo/` is still an unauthenticated Phase 1 smoke route; ticket-authenticated WebSockets arrive with Phase 4 (import progress) and Phase 11 (alerts).
- Frontend lint reports 3 fast-refresh warnings (context + hook exported from the same file).
- Phase 3: performance was measured once on 1M random rows, not on 6.36M PaySim rows or under concurrent load. Page-number paging gets slow at very deep pages (use `?cursor=`).
- Search is exact-match only (D-026). The transaction UI uses page-number paging only; it does not yet expose keyset mode.
- Phase 3 pages (Transactions, detail, account) are type-checked, built and component-tested, and the APIs were exercised live, but the pages were not opened in a browser.
- Datasets can be listed and created via API but there is no dataset-creation UI yet (arrives with the import wizard in Phase 4).
- Phase 4: import throughput is ~12k rows/s at 1M rows (target 20k) and was not measured at 6.36M rows; the real PaySim file has not been imported (needs your Kaggle download). Excel imports were tested with small files only (read-only streaming, but openpyxl is slower than CSV; limit 100 MB).
- Cancelling or failing an import keeps the rows from already-committed chunks (by design, for resume); there is no automatic rollback of a partial import.
- A job whose worker died stays `running` until someone force-resumes it (the UI offers this after 60 s without progress); there is no automatic stale-job reaper yet.
- Only the first 10,000 row errors per import are stored; the CSV error export covers only those.
- CSV row estimate for the progress bar counts newlines, so it can be off for files with line breaks inside quoted cells; the bar caps at 100%.
- Uploaded files stay on disk (`media/imports/`) after import; retention/cleanup is Phase 16. In production, upload storage must be shared between web and worker (volume/S3).
- No antivirus scan hook on uploads (type/size/magic-byte checks only).
- The backend test run prints a harmless teardown warning ("test database is being accessed by other users") after the async WebSocket tests.
- The import wizard and detail pages are component-tested and the API/WebSocket path was exercised live, but the pages were not opened in a browser.
- PaySim: 99.86% of senders appear once (max 3 transactions), so per-sender behavioural/graph features cannot be learned from it; cold-start handling is the realistic path (doc 19).
- PaySim fraud rate differs sharply across the chronological splits (0.082% train, 0.058% validation, 0.436% test); thresholds tuned on validation will not transfer cleanly. Reported as data drift, not hidden.
- ULB chronological validation/test contain only 55 / 52 frauds after de-duplication; metrics there carry wide uncertainty (bootstrap CIs required).
- Elliptic is not downloaded yet (needed for Phase 7B only).
- The PaySim balance-feature result (PR-AUC 0.989) reflects simulator accounting rules, not generalisable detection skill; the `core` result (0.194) is the cautious figure (doc 08).
- The registry's `code_commit` is the last committed hash at registration, which can precede uncommitted edits.
- Baseline latency covers model scoring only (not feature computation or I/O) and was measured inside Docker on a laptop CPU.
- PaySim `core+balance` is saturated (RF and XGBoost PR-AUC 1.000): it cannot compare algorithms and must not be quoted as real-world performance.
- ULB test has 52 frauds; LR, RF and XGBoost are indistinguishable there.
- Random Forest single-transaction latency (12 ms) reflects `n_jobs=-1` thread overhead, not model cost.
- `xgboost` brings a ~200 MB unused GPU dependency (`nvidia-nccl-cu13`); the Docker image is correspondingly larger.
- LOF and One-Class SVM see only 0.3–1% of PaySim train rows; the autoencoder did not early-stop within 15 epochs and may be under-trained. None of the 5C models was tuned.
- Saved models are joblib/pickle files: only load artifacts produced by this project (pickle executes code on load).
- The `torch` CPU wheel comes from an additional package index (`download.pytorch.org`), a supply-chain consideration to review before production.
- Detection scores raw model output (not calibrated probabilities); scores from different models are not comparable. Only PaySim-feature models can score platform data; the receiver-history features assume PaySim-style account references (`M…` = merchant) and need as much past data as training had (doc 08, Phase 5D).
- Detection runs score an entire dataset and store a `Prediction` row per transaction (capped at 2M rows); there is no single-transaction real-time scoring endpoint yet, no run cancellation, and no model activation/training API.
- The Anomaly Detection and Model Performance pages are component-tested only; there is no threshold slider, comparison chart or per-transaction score panel.
- The detection tests use small synthetic data; real-data checks were run manually (doc 08) and are not part of the automated suite.
- Behavioral deviation is not applicable to PaySim (every transaction is cold start); the engine is validated on a synthetic DEMO scenario and unit tests only, so its fraud-detection value is unmeasured. Weights, τ and thresholds are uncalibrated design choices (calibration: Phase 9).
- Behavior covers outgoing spending only; receiver-side profiles are descriptive. Hour of day is UTC (no per-account time zones). The scoring baseline uses the latest 500 prior transactions in 90 days (profiles use the whole window).
- Behavior runs are worker/API only (no UI to start one); a run scores a whole dataset (cap 2M rows) and stores a result row per transaction.
- Merchant-category behavior works only when a dataset supplies categories; none of the real datasets do.
- Graph scores are heuristic and uncalibrated; "proximity to flagged accounts" is not implemented; the graph-risk component G is not yet consumed by a risk score (Phase 9) and RQ2 (do graph features help detection?) is untested.
- On the real PaySim slice the graph detectors find only 84 weak fan-in patterns and no cycles/chains/clusters; they are validated on planted patterns in a synthetic DEMO dataset. Fraud evidence from graph patterns on PaySim is not demonstrated.
- Snapshots analyse a whole dataset (cap 2M transactions; cycle search has a 300k-expansion budget per run — `truncated` is reported); there is no incremental graph update.
- Neo4j projection: edges carry immutable fields only (status changes not projected), isolated accounts are not projected, no automatic scheduled sync (manual/API), and Neo4j was slower than PostgreSQL for neighborhoods on the measured data. Aura Free is too small for the PaySim slice.
- The relationship diagram is not rendered in tests or a browser; communities are shown only as ids/findings; no ranked-neighbour list.
- OCR and duplicate matching are validated only on clean machine-rendered synthetic invoices. Accuracy falls to 67.5% at 5° rotation and 50% at 4% noise (no deskew/denoise); real layouts, tables, stamps, handwriting and non-English text are untested. Currency symbols other than $ € £ ₹ and amounts in other number formats may be missed (fields are `null`, never guessed).
- Date parsing assumes day-first for numeric dates (12/03/2026 = 12 March); ambiguous formats can be misread, which is why a person verifies every invoice.
- Transaction duplicate detection found nothing on the real PaySim slice (no repeating senders); it is validated on constructed cases. Repeated-payment detection is per dataset, exact amount only, and flags at most 20,000 pairs per scan.
- Scores/thresholds/weights are uncalibrated. "Duplicate record alerts" are not built (Phase 11). The PDF report is plain (no charts or images) and its layout was not visually inspected.
- Stored invoices have no virus scan and no retention/deletion policy yet; scans are manual (no schedule); invoice matching is O(blocked pairs) and was tested on tens of invoices, not thousands.
- Risk weights, thresholds, the F and H definitions, and the normalisation of A are design choices; on the real PaySim slice the combined score was not better than the model score alone (RQ5 unresolved), and three of six components are unavailable for all PaySim transactions.
- Risk scoring is batch (whole dataset per run, cap 2M transactions) and reads the *latest* detection/behaviour/graph/duplicate results of the dataset; there is no per-transaction on-demand scoring, no alerts yet (Phase 11), and no `risk_category` filter on the transaction list.
- G visibility uses at most 50 listed transactions per finding; account-level graph metrics (PageRank, community) are not used by R. `neutral_prior` takes medians over a sample of at most ~50k transactions.
- The calibration tool is a CLI experiment; weights are searched on a coarse grid (step 0.1) over the components that vary; no UI for it.
- LIME is unstable and weakly faithful on the tree models tested (top-3 overlap between seeds 0.68–0.75; 17–46% agreement with SHAP). Isolation Forest, LOF, One-Class SVM and the autoencoder are explained only by LIME (no SHAP) and were not evaluated.
- RQ4's usability review (do people understand the explanations?) was not done; only technical stability and fidelity were measured, on one dataset slice and two XGBoost models.
- Explanations can only be produced for models whose features the platform can rebuild (PaySim features) and only while the stored prediction is reproducible; features such as sender history assume the dataset still holds the same earlier transactions.
- Contributions are in log-odds (XGBoost, logistic regression) or probability (forests) units and are not comparable between models. The PDF layout was not visually inspected. No counterfactual explanations, no explanation comparison UI, and no global-importance chart.
- Alert thresholds are uncalibrated design values, `high_value` is currency-agnostic (default 1,000,000 flooded the real PaySim slice: 8,225 alerts before the per-rule cap), and no alert precision/recall was measured. Alerts are produced only from stored engine results: they are as late as the last risk/behaviour/graph/duplicate run.
- Alerts are per dataset evaluation (no streaming); "account behaviour change" is the weekly spend-jump signal only; failed-transaction alerts need status data (PaySim has none). Email was tested against a local SMTP test server and the console/locmem backends, not a real provider; Notification preferences per user, snooze, reopen, bulk actions and case linking are not built.
- The dev database holds alerts generated from my own checks on the DEMO datasets and the PaySim slice; alert history is append-only by design, so they are only removable with TRUNCATE.
- Cases: no reopening of resolved cases, no bulk actions, no email to assignees, no embedded graph or account-history panel in the workspace (links only), no SLA/ageing alerts, and automatic cases rely on alert severity only. Evidence has no virus scan and no retention/deletion policy yet (Phase 16); files live on the application's media storage, which must be shared by web and worker and backed up. The four-eyes closure option is built but off by default pending your decision (D-014).
- The Investigations UI and the closure PDF were not opened in a browser / visually inspected; the PDF text and structure are tested.
- Analytics: the rollup is refreshed hourly (or on demand), so the dashboard can lag recent imports by up to an hour; "flagged" and risk categories come from each dataset's latest succeeded detection / risk run only. Days are UTC calendar days. The investigator-decision false-positive rate only counts decided items, and on a small decided sample it is noisy. The labelled research view exists only where `ground_truth_label` is present. No dashboard mini-graph (FR-M10-10). Exports are synchronous (capped at 2,000 PDF rows) and have no scheduled delivery.
- Phase 15: no automated dependency audit, penetration test or multi-user load test was run; performance numbers are single-user, sequential, on one machine with 363k transactions (see doc 20). The browser E2E suite is not in CI. NFR-01 (import 20k rows/s) remains missed and the 6.36M-row import/rollup are unmeasured. import-linter (NFR-11) is not configured.
- Phase 16: the production stack was rehearsed on one machine only (self-signed local CA); no cloud deployment, real-domain certificate, SMTP delivery or Neo4j production profile was tested. The production image is large (torch with CUDA libraries). Backups are a script you must schedule and copy off-site; the drill used a tiny database. RQ1, RQ2 and RQ6 were never executed (doc 23). The CSP depends on a build-time patch of claygl (D-104).
- Dev environment (2026-11-20): the Neo4j projection of dataset 9 is stale/unavailable: the Neo4j data volume was created with the earlier password and the current `.env` has `NEO4J_PASSWORD=change-me`, so the app gets `AuthError` / `AuthenticationRateLimit`. Graph pages are unaffected (PostgreSQL is the default source). Fix: restore the original password in `.env`, or reset the volume (`docker compose stop neo4j && docker volume rm finguard_neo4jdata && docker compose up -d neo4j`) and run `manage.py rebuild_neo4j 9`.
- Signup (Phase 17): no CAPTCHA or bot challenge (rate limits only: 5 registrations per hour per client); verification and reset emails need working SMTP in production (development prints them in the worker log); there are no organisations or separate workspaces, so every approved user sees the same data; no MFA; no self-service profile or password change page for signed-in users; approvals have no expiry or reminder.
